# Audit technique — Dictionnaire Tadaksahak

## Périmètre

L’audit compare l’archive fournie le 7 septembre 2026 avec le dépôt `terpoland4-star/Dictionnaire-Tadaksahak`. Le dépôt GitHub n’est pas seulement un site statique : `main` contient maintenant un monorepo avec `apps/web` et `apps/api`. L’archive correspond à un état antérieur du frontend, à la racine, avec un `app.js` monolithique.

## Diagnostic

| Domaine | Constat | Décision |
| --- | --- | --- |
| Frontend | PWA statique sans build obligatoire, données JSON chargées côté navigateur | Conservé, car adapté à Termux, GitHub Pages et un VPS peu coûteux |
| JavaScript | L’ancien `app.js` monolithique a déjà été découpé en modules ES | Conservé, avec contrôles de syntaxe automatisés |
| Backend | API Express/PostgreSQL limitée aux contributions | Conservée comme composant optionnel, sans déplacer la recherche du dictionnaire |
| Données | JSON valides, mais plusieurs ressources concurrentes et références cassées | Normalisation des chemins et une source canonique par usage |
| Ressources | Doublons binaires, noms avec espaces/accents, doubles extensions PDF/JPG | Renommage URL-safe et suppression des doublons prouvés |
| Déploiement | Port API documenté mais absence de preuve sur le VPS réel | `3003` conservé comme port interne ; vérification à faire sur le VPS avec `ss` |
| Qualité | Pas de tests, CI ou audit reproductible | Ajout de `npm run check` et `scripts/audit.mjs` |

## Corrections appliquées

Les fichiers PDF `*.pdf.pdf` et l’image `couverture_idaksahak.jpg.jpg` ont été renommés. Les fichiers image identiques présents dans plusieurs dossiers ont été réduits à une copie canonique. Les références ont été mises à jour, notamment celles de la galerie et des livres. Les pages HTML de livres ont été rendues autonomes en supprimant leurs scripts inexistants et en corrigeant leurs chemins relatifs.

Les trois illustrations annoncées dans `data/livres.json` mais absentes du dépôt ont été retirées des métadonnées plutôt que remplacées par une image trompeuse. Elles pourront être réintroduites lorsque les fichiers et leurs droits de diffusion seront disponibles.

L’API valide désormais le port, refuse un secret JWT par défaut en production, limite la taille JSON à 32 ko, gère explicitement CORS, renvoie un 404 JSON, arrête proprement le serveur et capture les erreurs des routes asynchrones. Les entrées de contribution sont bornées et l’identifiant de validation est contrôlé.

## Vérifications effectuées

`npm run check` passe avec les résultats suivants :

- syntaxe JavaScript valide pour tous les fichiers `apps/` ;
- parsing valide des 19 fichiers JSON ;
- aucune référence locale manquante détectée ;
- aucune duplication binaire applicative restante, à l’exception des fichiers `.keep` intentionnels.

Le port `3003` n’était pas occupé dans l’environnement d’audit. Ce résultat ne vaut pas pour le VPS : l’installation doit être précédée de `ss -ltnp | grep -E ':(80|443|3003)\\b' || true` sur le VPS lui-même.

## Risques restants

L’audit ne valide pas la qualité linguistique, les traductions, les licences des images et PDF, ni la conformité des textes académiques. Il n’existe pas encore de test navigateur, de CI GitHub, de sauvegarde PostgreSQL documentée ou de procédure de rotation des secrets. Ces sujets sont prioritaires avant l’ouverture publique de l’API.

## Recommandation de déploiement

Servir `apps/web` via Nginx ou Caddy sur HTTPS et garder Node/PostgreSQL sur le réseau local. Publier l’API sous `/api/` du même domaine avec un reverse proxy, plutôt que d’exposer directement le port Node. Le frontend reste statique et peut continuer à être déployé indépendamment de l’API.
